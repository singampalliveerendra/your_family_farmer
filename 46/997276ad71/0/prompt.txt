The core principle

The thing that must be separate is the database, not just the website. If real farmers and the client both write to the same Supabase, test orders, fake payments, and junk produce will pollute real farmer data. So "two environments" really means two Supabase projects + two Vercel deploys, wired by environment variables.

Recommended setup: one repo, two environments off branches

This is the simplest thing that works with what you already have (single Vercel project deploying from main).

┌────────────────────────┬───────────────────────────┬──────────────────────────────┐
│                        │ Production (real farmers) │   Staging (client testing)   │
├────────────────────────┼───────────────────────────┼──────────────────────────────┤
│ Branch                 │ main                      │ staging (new)                │
├────────────────────────┼───────────────────────────┼──────────────────────────────┤
│ URL                    │ yourfamilyfarmer.com      │ staging.yourfamilyfarmer.com │

│ Supabase               │ current project           │ new "YFF-Staging" project    │
├────────────────────────┼───────────────────────────┼──────────────────────────────┤
│ Razorpay               │ live keys                 │ test-mode keys               │
├────────────────────────┼───────────────────────────┼──────────────────────────────┤
│ SMS (Fast2SMS/2Factor) │ live keys                 │ test/throwaway or disabled   │
├────────────────────────┼───────────────────────────┼──────────────────────────────┤
│ Data                   │ real                      │ disposable                   │
└────────────────────────┴───────────────────────────┴──────────────────────────────┘

Flow: you build on a feature branch → merge to staging → client tests at staging.yourfamilyfarmer.com → once approved, merge staging → main → real farmers get it. Clean promotion path.

Why a second Supabase project (not just a second branch on one DB)

- Test orders never touch real farmers. The client can create fake harvests, cancel orders, trigger refunds — zero risk.
- You run new migrations on staging first. Your workflow already has a pile of pending *-migration.sql scripts (platform-fee, follows, harvest-shelf). Staging becomes the place to prove a migration before it hits real data — no more "run this SQL in prod and hope."
- Supabase free tier allows 2 projects, so this can cost ₹0 to start.

Critical: staging must NOT send real SMS or take real payments

This is the part people forget. With the same keys, a client's test order will:
- fire a real Fast2SMS/2Factor SMS to whatever number they type, and
- hit real Razorpay.

So staging needs Razorpay test-mode keys and either test SMS keys or SMS disabled. Everything else (SESSION_SECRET, MODERATOR_PASSWORD, etc.) just gets its own staging value in Vercel's "Preview/Staging" env scope.
